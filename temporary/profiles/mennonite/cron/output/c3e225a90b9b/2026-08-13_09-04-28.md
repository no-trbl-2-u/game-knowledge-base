# Board Game Rules Research

Use this skill when the task is to locate, verify, extract, or summarize official tabletop game rules. The purpose is not merely to find a likely PDF. The purpose is to establish provenance and produce usable evidence for a knowledge base or design decision.

## Core doctrine

BoardGameGeek is a discovery layer, not the courthouse of record. Use it for metadata, ratings, mechanics tags, forums, versions, and leads. Do not assume it hosts the complete or current rules.

For actual rules, prefer this source order:

1. Publisher/product page
2. Publisher-hosted downloads/resources/FAQ/errata pages
3. Official linked files on trusted storage/CDN platforms
4. BGG files/forum links as secondary leads
5. Retail pages, fan aids, rules summaries, and videos only when official sources fail

## Workflow

1. Identify the exact game and edition/expansion.
   - Normalize title variants.
   - Watch for standalone expansions, decks, promos, revised editions, and campaign variants.

2. Search broadly, then narrow to official provenance.
   - Query title + `rules`, `rulebook`, `PDF`, `publisher`, and expansion/deck name.
   - Prefer publisher product pages even when the PDF itself lives on Dropbox, Google Drive, or a CDN.

3. Verify the file, not just the link.
   - Download or open the target.
   - Confirm it is a rulebook/rules reference, not a marketing sheet or play aid.
   - Record file type, page count, size, version/date if present, and whether text extraction works.

4. Extract enough text to prove identity.
   - Capture title page lines, version, table of contents, and any relevant mechanics headings.
   - Do not mirror the whole copyrighted rulebook unless the user specifically has rights or asks for private analysis within fair-use limits.

5. Report with provenance.
   - Official product/source URL
   - Direct rulebook URL if available
   - Verification evidence
   - Any caveats: version ambiguity, expansion dependency, fan-made status, inaccessible file, or missing errata

6. For KB ingestion, store source metadata separately from extracted mechanics summaries.
   - `source_url`
   - `rulebook_url`
   - `publisher`
   - `edition/version`
   - `retrieved_at`
   - `extraction_status`
   - `citation snippets`
   - `mechanics schema / normalized summary`

## KB ingestion and maintenance audit

When research is being added to a structured knowledge base or an existing maintenance PR is being audited:

1. Audit the exact live commit, not the PR description or an earlier audit. Reopen every consequential source and inspect the complete changed-file set.
2. Treat every non-null metadata value as a claim. A rating, complexity weight, edition, player count, or status must have a declared source in that document's own registry and an explicit evidence path; a source mentioned only in a sibling ledger is not enough.
3. Separate source roles: official rules establish rules, independent reviews establish reception, BGG supplies discovery/rating metadata, and visuals require their own provenance and hash checks.
4. Keep edition scope explicit when comparing revised printings. A later rulebook may be evidence of a revision, but it must not silently become authority for the target edition.
5. Do not turn an open denominator into invented completeness. Descriptive coverage may remain `UNKNOWN` when the governing face/card inventory was not retrieved; reject unsupported claims, not honest sparsity.
6. Verify the visual packet itself: recompute hashes, inspect the contact sheet first, then confirm individual panels are meaningful, reduced, source-linked, and non-substitutive.
7. Record a verdict that names the exact defect, the cheapest repair, a discriminating test, and an abort condition. Green structural CI does not cure unsupported semantic metadata.
8. Treat retrieval receipts as auditable claims, not permanent truth. Re-fetch every consequential URL at audit time and compare status, content type, byte length, and SHA-256. Dynamic HTML pages commonly drift while retaining the same URL and visible claim; if the recorded payload cannot be reproduced, mark the receipt defective unless a stable archive/static replacement is inspected and all dependent claims are rebound.
9. Separate reproducible-source failure from semantic-source failure. A fresh hash mismatch is not by itself proof that the underlying fact changed, but it is proof that the committed custody record no longer proves what it asserts. Require a new receipt or a narrowed claim before approval/promotion.
10. For exact-head PR audits, treat expected pre-approval completion failures as workflow state, not packet defects: a `ready_for_audit` intake is legally unpromoted until the Mennonite adds approval. Audit the packet's sources and claims before judging the expected completion check.

## KB maintenance audit procedure

For an existing-game maintenance PR, treat the live PR head as the only auditable object:

1. Start from a clean checkout, fast-forward local `main` to `origin/main`, and record base/head SHAs.
2. List open PRs and select one eligible maintenance PR; exclude new-game intake, intake-gap reports, administrative cleanup, and already-closed work.
3. Fetch the PR head and verify local detached HEAD, PR ref, remote branch, and GitHub's live head SHA are identical. Inspect the complete diff and commit topology.
4. Reopen every consequential source, including official rules, FAQ/errata, independent review, rating source, and visual source. Recompute recorded hashes where possible and preserve edition boundaries.
5. Treat every non-null frontmatter value as a claim. A source in a sibling ledger does not support metadata in another document: each affected document must declare the source in its own registry, and consequential metadata needs an explicit claim/evidence path.
6. Inspect the contact sheet before individual visual assets; recompute asset hashes and confirm the packet is meaningful, reduced, source-linked, and non-substitutive.
7. Run repository gates in a disposable audit worktree when validators/generators write telemetry. Wrap hard gates with the repository's fail-closed runner. Green structural CI does not cure unsupported semantic metadata.
8. For a repairable defect, post `REVISE` on the same PR with assumption, failure, evidence, cheapest test, mitigation, and abort condition. Do not repair semantic research, commit rejection records, approve, or merge.
9. Recheck the live head and comment delivery after posting. End the audit checkout clean and report exact commands, SHAs, source results, files changed, and merge disposition.

See `references/maintenance-audit-field-pattern.md` for a reusable exact-head audit pattern and provenance examples.

## Pitfalls

- Do not stop at BGG when BGG lacks files. Search the publisher and linked product resources.
- Do not treat a third-party summary as rules unless no official rules are accessible.
- Do not conflate base-game rules with expansion/deck-specific rules.
- Do not claim a rulebook is verified until you have inspected the file contents.
- Do not build a KB around one source class. Publisher pages, BGG metadata, files, errata, and community discussions each answer different questions.
- Do not assume a source declared in `sources.okf.md` automatically supports metadata in `index.okf.md`; audit each document's frontmatter registry and claim path independently.
- Do not accept a green validator or CI check as proof that a rating, weight, edition, or other semantic field is truthfully sourced.
- Do not let a telemetry-writing gate dirty the authoritative audit checkout; run it in a disposable worktree or restore only generated audit residue after inspection.

# GitHub Pull Request Workflow

### Quick Auth Detection

```bash
# Determine which method to use throughout this workflow
if command -v gh &>/dev/null && gh auth status &>/dev/null; then
  AUTH="gh"
else
  AUTH="git"
  # Ensure we have a token for API calls
  if [ -z "$GITHUB_TOKEN" ]; then
    if [ -f ~/.hermes/.env ] && grep -q "^GITHUB_TOKEN=" ~/.hermes/.env; then
      GITHUB_TOKEN=$(grep "^GITHUB_TOKEN=" ~/.hermes/.env | head -1 | cut -d= -f2 | tr -d '\n\r')
    elif grep -q "github.com" ~/.git-credentials 2>/dev/null; then
      GITHUB_TOKEN=$(grep "github.com" ~/.git-credentials 2>/dev/null | head -1 | sed 's|https://[^:]*:\([^@]*\)@.*|\1|')
    fi
  fi

```

### Extracting Owner/Repo from the Git Remote

Many `curl` commands need `owner/repo`. Extract it from the git remote:

```bash
# Works for both HTTPS and SSH remote URLs
REMOTE_URL=$(git remote get-url origin)
OWNER_REPO=$(echo "$REMOTE_URL" | sed -E 's|.*github\.com[:/]||; s|\.git$||')
OWNER=$(echo "$OWNER_REPO" | cut -d/ -f1)
REPO=$(echo "$OWNER_REPO" | cut -d/ -f2)
echo "Owner: $OWNER, Repo: $REPO"
```

### PR Preflight: Avoid Stale or Conflicting Branches

Before pushing or creating a PR from local work, always fetch the remote base and inspect divergence. A branch that is merely "ahead 1" of an old `main` can still produce a conflicting PR if `origin/main` advanced.

When useful work accidentally landed on a stale or dirty branch, do not merge the whole branch by reflex. Salvage the intended commit(s) onto a clean `origin/main` worktree, resolve only the resulting conflicts, and leave the user's source branch untouched. See `references/stale-branch-salvage.md` for the full pattern.

For existing PR conflict-resolution requests, check publish authority before investing in the rebase. `maintainerCanModify: true` on a cross-repo PR is not enough if the authenticated account has only read access to the base repo and cannot push to the contributor fork. Run `gh repo view OWNER/REPO --json viewerPermission --jq .viewerPermission` and inspect the PR head repo before promising to push or merge. If publishing is blocked, preserve the resolved commit with `git format-patch` and report the patch path, local branch, verification result, and exact permission blocker. See `references/conflict-resolution-permission-gate.md`.

When the user says the conflicting PR branch is the new source of truth for a domain, do not blindly take all `--ours`. Inspect conflict stages (`:1:`, `:2:`, `:3:`), preserve the PR's canonical domain document, take current `origin/main` for implementation/status history where it is newer, verify no conflict markers remain, run full local verification, push, and wait for GitHub mergeability/checks. See `references/pr-conflict-resolution-source-of-truth.md`.

```bash
# From the repo root
CURRENT_BRANCH=$(git branch --show-current)
git fetch origin main

git status --short --branch
git log --oneline --decorate --max-count=5

# If work was committed directly on main, move it to a branch, then update main.
if [ "$CURRENT_BRANCH" = "main" ]; then
  git switch -c <topic-branch>
  git switch main
  git pull --ff-only origin main
  git switch <topic-branch>
fi

# Rebase topic branch onto the current remote base before opening the PR.
git rebase origin/main
```

If rebase conflicts appear, resolve them before creating the PR. If the remote already contains newer planning/spec changes that supersede the local commit, abort the rebase and ask whether to close the stale PR rather than forcing obsolete plan text through.

After PR creation, verify mergeability immediately:

```bash
gh pr view --json number,url,state,mergeable,headRefName,baseRefName,statusCheckRollup
gh pr checks || true
```

Do not report a PR as ready until mergeability and checks have been inspected. If GitHub reports `CONFLICTING`, say so plainly and name the conflicted files.

## 4. Monitoring CI Status

### Check CI Status

**With gh:**

```bash
# One-shot check for the current branch/PR
gh pr checks

# If you know the PR number, target it explicitly. This avoids ambiguity
# when the working tree has moved or multiple PRs exist.
gh pr checks <PR_NUMBER>

# Watch until all checks finish. Use a short interval when the user is waiting.
gh pr checks <PR_NUMBER> --watch --interval 5
```

When the user says to "try running it" before creating or finishing a PR, run the repo's local verification command first, then create/push the PR, then watch CI to completion. Do not call the PR ready until both local verification and GitHub checks have passed or any failure has been named plainly.

**With git + curl:**

```bash
# Get the latest commit SHA on the current branch
SHA=$(git rev-parse HEAD)

# Query the combined status
curl -s \
  -H "Authorization: token $GITHUB_TOKEN" \
  https://api.github.com/repos/$OWNER/$REPO/commits/$SHA/status \
  | python3 -c "
import sys, json
data = json.load(sys.stdin)
print(f\"Overall: {data['state']}\")
for s in data.get('statuses', []):
    print(f\"  {s['context']}: {s['state']} - {s.get('description', '')}\")"

# Also check GitHub Actions check runs (separate endpoint)
curl -s \
  -H "Authorization: token $GITHUB_TOKEN" \
  https://api.github.com/repos/$OWNER/$REPO/commits/$SHA/check-runs \
  | python3 -c "
import sys, json
data = json.load(sys.stdin)
for cr in data.get('check_runs', []):
    print(f\"  {cr['name']}: {cr['status']} / {cr['conclusion'] or 'pending'}\")"
```

### Poll Until Complete (git + curl)

```bash
# Simple polling loop — check every 30 seconds, up to 10 minutes
SHA=$(git rev-parse HEAD)
for i in $(seq 1 20); do
  STATUS=$(curl -s \
    -H "Authorization: token $GITHUB_TOKEN" \
    https://api.github.com/repos/$OWNER/$REPO/commits/$SHA/status \
    | python3 -c "import sys,json; print(json.load(sys.stdin)['state'])")
  echo "Check $i: $STATUS"
  if [ "$STATUS" = "success" ] || [ "$STATUS" = "failure" ] || [ "$STATUS" = "error" ]; then
    break
  fi
  sleep 30
done
```

## 5. Auto-Fixing CI Failures

When CI fails, diagnose and fix. This loop works with either auth method.

### Step 1: Get Failure Details

**With gh:**

```bash
# List recent workflow runs on this branch
gh run list --branch $(git branch --show-current) --limit 5

# View failed logs
gh run view <RUN_ID> --log-failed
```

**With git + curl:**

```bash
BRANCH=$(git branch --show-current)

# List workflow runs on this branch
curl -s \
  -H "Authorization: token $GITHUB_TOKEN" \
  "https://api.github.com/repos/$OWNER/$REPO/actions/runs?branch=$BRANCH&per_page=5" \
  | python3 -c "
import sys, json
runs = json.load(sys.stdin)['workflow_runs']
for r in runs:
    print(f\"Run {r['id']}: {r['name']} - {r['conclusion'] or r['status']}\")"

# Get failed job logs (download as zip, extract, read)
RUN_ID=<run_id>
curl -s -L \
  -H "Authorization: token $GITHUB_TOKEN" \
  https://api.github.com/repos/$OWNER/$REPO/actions/runs/$RUN_ID/logs \
  -o /tmp/ci-logs.zip
cd /tmp && unzip -o ci-logs.zip -d ci-logs && cat ci-logs/*.txt
```

### Step 2: Fix and Push

After identifying the issue, use file tools (`patch`, `write_file`) to fix it:

```bash
git add <fixed_files>
git commit -m "fix: resolve CI failure in <check_name>"
git push
```

### Step 3: Verify

Re-check CI status using the commands from Section 4 above.

### Auto-Fix Loop Pattern

When asked to auto-fix CI, follow this loop:

1. Check CI status → identify failures
2. Read failure logs → understand the error
3. Use `read_file` + `patch`/`write_file` → fix the code
4. `git add . && git commit -m "fix: ..." && git push`
5. Wait for CI → re-check status
6. Repeat if still failing (up to 3 attempts, then ask the user)

### CI/Local Parity Pitfalls

Local green does not acquit the branch if the local dependency tree was borrowed, symlinked, or otherwise not freshly installed from the lockfile. Before reporting a CI mismatch as mysterious, reproduce CI conditions in the PR worktree:

```bash
rm -rf node_modules
npm ci
npm run typecheck
npm run verify
```

For Node/TypeScript projects, a symlinked `node_modules` from another checkout can mask package-version drift. If CI fails on types that local verification missed, suspect dependency parity first, then patch the actual code/test contract.

Visual smoke gates deserve two separate readings:

- missing baselines / screenshot diffs may be an approval workflow issue;
- console errors during smoke are runtime defects and should be fixed before declaring the PR ready, even when the script exits with a baseline-related code.

## 6. Merging

**With gh:**

```bash
# Squash merge + delete branch (cleanest for feature branches)
gh pr merge --squash --delete-branch

# Enable auto-merge (merges when all checks pass)
gh pr merge --auto --squash --delete-branch
```

**With git + curl:**

```bash
PR_NUMBER=<number>

# Merge the PR via API (squash)
curl -s -X PUT \
  -H "Authorization: token $GITHUB_TOKEN" \
  https://api.github.com/repos/$OWNER/$REPO/pulls/$PR_NUMBER/merge \
  -d "{
    \"merge_method\": \"squash\",
    \"commit_title\": \"feat: add user authentication (#$PR_NUMBER)\"
  }"

# Delete the remote branch after merge
BRANCH=$(git branch --show-current)
git push origin --delete $BRANCH

# Switch back to main locally
git checkout main && git pull origin main
git branch -d $BRANCH
```

Merge methods: `"merge"` (merge commit), `"squash"`, `"rebase"`

### Enable Auto-Merge (curl)

```bash
# Auto-merge requires the repo to have it enabled in settings.

```
