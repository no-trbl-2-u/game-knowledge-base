## Mainline Freshness and Branch Discipline

Before synthesizing state, fetch the remote and establish whether the current checkout is trustworthy:

```bash
git fetch origin --prune
git status --short --branch
git rev-list --left-right --count HEAD...origin/main
```

If the current branch is stale, diverged from `origin/main`, is an old oversight branch, or has local work that should not be disturbed, do **not** audit that stale checkout. Inspect current `origin/main` instead, preferably in a temporary detached worktree when the live checkout has uncommitted changes:

```bash
git worktree add --detach /tmp/<repo>-oversight origin/main
# run all audit commands with workdir=/tmp/<repo>-oversight
```

A direct detached checkout is acceptable only when it will not trample local work:

```bash
git switch --detach origin/main
# or, when edits are likely:
git switch -c oversight/<short-topic> origin/main
```

Report this plainly in the brief. Stale local branches are a first-class oversight hazard: the point of oversight is judgment over the present campaign, not a fossil.

When auditing from a temporary worktree, remember that dependencies may not be present there. If `verify`, `playtest`, `deploy:check`, or equivalent fails because `node_modules` / `tsc` / `ts-node` is absent in the worktree, resolve the worktree setup first and rerun before declaring the gate red. For mechanics, temporarily symlinking the main checkout's `node_modules` can be acceptable for build/deploy/playtest gates; remove temporary dependency symlinks before reporting the worktree clean. For mobile / Expo / expo-router checks, prefer a real install in the detached worktree (`npm ci` or the repo's package-manager equivalent) over symlinking `node_modules`: symlinked dependencies can cause Metro/Expo to resolve routes through the source checkout and produce false setup errors such as `No routes found`. Distinguish worktree setup failure from product failure.

When plan/document edits are needed, prefer a short-lived `oversight/<topic>` branch from current `origin/main`, push it, open a PR, and verify mergeability/checks. Do not push directly to `main` unless T explicitly asks for direct mainline mutation and the repo convention allows it.

If useful Axiomancer work lands on the wrong stale branch and T wants it on `main`, preserve the dirty/stale source branch. Use a clean worktree from `origin/main`, cherry-pick only the intended commit(s), and resolve plan conflicts by keeping current mainline chronology while carrying forward any new still-relevant finding. See `github-pr-workflow` → `references/stale-branch-salvage.md`.

See `references/mobile-mainline-pr-oversight.md` for the session pattern that motivated this rule.
